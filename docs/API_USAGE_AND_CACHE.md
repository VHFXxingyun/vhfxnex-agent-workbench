# API 用量与缓存命中说明

更新时间：2026-11-15

本说明用于区分 DeepSeek 返回的缓存遥测、VHFXNEX 派生的命中指标和当前价费用估值。费用最终以 DeepSeek 开放平台账单为准。

## 三个缓存指标

| 指标              | 计算方式                                                  | 适合回答的问题               |
| ----------------- | --------------------------------------------------------- | ---------------------------- |
| 命中请求率        | 至少命中 1 个输入 Token 的请求数 ÷ 已返回缓存统计的请求数 | 有多少请求复用过缓存？       |
| 输入 Token 命中率 | 缓存命中输入 Token ÷ 已返回缓存统计的输入 Token           | 被统计的输入里有多少被复用？ |
| 统计覆盖率        | 已返回缓存统计的输入 Token ÷ 全部输入 Token               | 命中率覆盖了多少实际输入？   |

命中请求率不等于省钱比例。例如 100 次有遥测的请求里 50 次各命中 1 Token，请求命中率是 50%；如果总输入有 100,000 Token，输入 Token 命中率却只有 0.05%，省下的输入费很少。反过来，一次长请求命中大部分输入，命中请求率可能很低，但被复用的 Token 数和节省会较大。

没有缓存字段的请求不会被算成未命中，也不会放进前两个指标的分母；其输入仍进入覆盖率分母。因此解读命中率时，应先看统计覆盖率。低覆盖时，命中率只能代表那部分有遥测的请求。

## 如何读平台用量总览

- API 请求数是调用次数，Token 总量是输入与输出的总和；这两个汇总值没有缓存命中/未命中的分布，不能单独推出命中率。
- 账户余额、累计消费与图表所选时间范围的消费是不同口径。对账时应统一 API Key、时区和日期范围，并查看逐日/逐请求账单；平台页面注明数据可能延迟，不能把汇总差额直接归因于缓存。
- 命中是否省钱要看命中的输入 Token 数、未命中输入 Token 数、输出 Token 数、实际模型和调用时段。仅凭总消费和总 Token 数无法还原历史缓存命中率或精确解释费用。
- VHFXNEX 管理页的来源分组只覆盖本应用记录到的请求；DeepSeek 控制台选择“全部”时还可能包含该账户其他 API Key 或其他客户端的调用，二者不能直接等同。

## DeepSeek 缓存和计费

DeepSeek 自动进行上下文缓存，匹配的是从输入起始位置开始、完全相同的前缀单元，不是语义相似的内容。第一次请求可能只建立缓存；缓存需要时间持久化，并按 best-effort 提供，既不保证命中，也可能在数小时到数天后清理。详情见 [DeepSeek 上下文缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。

截至 2026-11-15，官方 DeepSeek V4.1 Flash 公开单价（美元/百万 Token）如下。具体高峰时段与节假日规则以[官方价格表](https://api-docs.deepseek.com/quick_start/pricing/)为准。

| Token 类型     | 非高峰 |   高峰 |
| -------------- | -----: | -----: |
| 输入缓存命中   | $0.003 | $0.006 |
| 输入缓存未命中 |  $0.15 |  $0.30 |
| 输出           |  $0.60 |  $1.20 |

因此，每个被缓存命中的输入 Token 在此价格表下比未命中便宜 50 倍，即少付约 98% 的该 Token 输入费。缓存只影响输入 Token；输出 Token 仍按输出价计费。供应商报告的思考 Token 是输出 Token 的组成部分，不能重复相加。DeepSeek 的 Search / Fetch 工具若被调用，还会按成功请求另行收费；VHFXNEX 当前使用自己的网页搜索适配器时，不应把这项费用自动套到应用搜索上。

按已知用量计算时：

```text
当前价输入/输出费用 ≈
(命中输入 Token × 命中单价
 + 未命中输入 Token × 未命中单价
 + 输出 Token × 输出单价) ÷ 1,000,000
```

如果缓存字段缺失、模型不在当前价格表内，或历史价格与当前价格不同，就不能从 Token 总量精确还原历史扣款。VHFXNEX 管理页面显示的是当前价估值区间，不是历史账单；实际金额、汇率和赠送额度以供应商控制台为准。

## VHFXNEX 的受控测量样本

2026-11-14 的 17 次受控直接 API/SDK 前缀探测中，9 次至少命中 1 个输入 Token，命中请求率为 52.9%；合计 7,891 个输入 Token 中有 3,456 个命中，输入 Token 命中率为 43.8%。按非高峰输入价估算，这 3,456 个命中 Token 相较全部未命中约少付 $0.00051；高峰价约少付 $0.00102。

这是小样本前缀探测，只说明那组相同前缀在该次测试中可复用，不代表完整浏览器工作流、之后的真实账号使用或长期命中率，也不能推算用户的整月账单。冷启动、新账号、不同账户、提示前缀变化、上下文中较早内容变化以及缓存过期都会影响命中。

## 在应用里查看

管理员可打开“管理控制台 → AI 调用趋势 → 按 Agent 来源查看用量与缓存”。先看统计覆盖率，再比较命中请求率和输入 Token 命中率，并按规划、对话、工作台和代码复核来源检查输入/输出 Token。若关注费用，还要看输入与输出分别占多少；只有命中请求率不足以解释费用。

管理员手动检查 DeepSeek 连接时，应用通过官方模型目录 `GET /models` 验证凭证和当前模型是否可用，不再生成 `OK` 聊天回复，因此不会产生该诊断回复的输入/输出 Token；连接检查也不写入 Token 用量账本。历史账本中的旧连接诊断行仍保留，不代表新检查会生成模型 Token。模型目录接口的细节见 [DeepSeek 官方模型列表 API](https://api-docs.deepseek.com/api/list-models/)。

应用只保存 Token 数、缓存统计、模型、请求耗时及来源，不保存提示词或思考文本。跨账户缓存按稳定伪名隔离：这有利于隐私，但减少了不同账户偶然复用同一前缀的机会。项目在规划、对话、工作台和代码复核 Agent 前共享静态提示前缀，尽量让同一账户的固定规则可复用；是否实际命中仍以供应商返回的缓存字段为准。

工作台需要连续多次调用模型时，后续工具步骤会先发送本轮不变的附件文本与图片，再发送每一步都会变化的任务检查点。这样附件在同一工作区、同一 `user_id`、内容和顺序不变时有机会形成可复用的前缀；如果把变化中的工具状态放在附件之前，缓存匹配通常会在状态变化处中断。该调整不会减少工作台请求次数或输出 Token，也不保证缓存命中；冷启动、附件变化和供应商缓存的 best-effort 行为仍会影响结果。当前只完成结构与本地回归检查，没有为测量效果额外调用 API。

对话 Agent 的每次模型请求最多携带最近 8 条历史消息、每条最多 1,000 字符；完整聊天仍保存在工作区，目标、路线、任务进度和近期成果则通过单独的精简状态摘要提供。纯进度问题继续由服务器直接读取状态回答，不发模型请求。这样限制重复发送的大段旧聊天，不影响工作台读取完整任务和附件；较早的聊天细节不一定进入模型上下文，用户可在当前指令里重述需要保留的细节。

工作台的后续工具步骤会重复发送检查点。检查点已经包含当前目标和本轮指示，因此额外历史不再重复完全相同的当前消息，并限制为最近 3 条此前用户指示、每条最多 800 字符；历史文本上限由最多 9,600 字符降至 2,400 字符（最多减少 75%）。这只压缩重复输入，不减少完成工作所需的模型请求，也不改变工作区保存的完整聊天。更早的细节如果未进入目标、约束、任务或附件，可能不进入每一步的模型上下文；用户可在本轮指示中重述。

工作台还会把稳定的工作区目标与本轮补充指示分开提供。此前内部拼接后的 `goal + 补充指示` 又和单独的 `instruction` 一起发送，可能在初始请求及每个后续检查点重复计入同一段指示；现在仅传一次目标字段和一次指示字段。该节省随指示长度和执行步数变化，不减少必要工具步骤。已有工作区状态与原始对话仍完整保存。

管理员收到明确的“打开文档/代码/表格工作台”指令时会直接分流，不再发起一次模型路由请求；讨论工具功能、模糊表达和需要判断的自然语言仍交给管理员 Agent。该快捷路由不改变工作区访问校验，也不会调用模型。管理员的“现在后台有项目在运行吗/做到哪里了”状态问题由服务器读取执行状态直接回答；在全局范围明确打开直接工具也不调用模型。

全局总控需要判断自然语言、把工作路由到某个既有项目或回答一般问题时仍会调用模型。项目分流最多提供当前用户有编辑权限的 12 个工作区；每个项目只带 220 字符目标摘要、名称、类别和路线，完整项目内容仍保留在工作区，模型给出目标后服务端再次验证工作区归属/编辑权限，才会排队。只读项目不会提供给调度器；若没有明确匹配目标，总控应询问用户，不会猜测。用户用“新建目标：……”等明确格式启动项目时，管理员直接交给规划器，省去前置的模型意图分类调用；规划器仍正常生成路线。全局聊天在服务端按用户分别保存，最多保留 40 条且总量不超过 100 KB；新对话会清除该用户当前总控会话，交接到项目时也会把本轮指令记录在对应工作区。

直接工具（文档、PDF、代码、CSV/Excel、演示稿、JSON）在用户编辑、校验、格式化、静态预览和下载时不调用模型；工具草稿通过账号隔离的浏览器 `localStorage` 自动保存，也不上传服务端或 DeepSeek。PDF 工具箱在浏览器内存中合并、重排或提取页面，不上传文件，也不调用模型。草稿恢复完成前编辑区暂不可操作；切换页面或关闭标签页时，会尽力立即写入最新已提交的编辑状态，减少防抖自动保存期间离开导致的内容回退。代码工坊使用 CodeMirror 6 提供常见 Web、脚本和数据文件的语法高亮、行号、折叠与键盘编辑；网页预览用与成果查看器相同的静态隔离器实时显示桌面/手机视口，运行脚本、表单提交、外部跳转和网络请求均禁用。ZIP 源码保持原样，需由用户在本地运行。演示稿工坊可逐页编辑、排序、添加演讲备注并导出 PowerPoint，PPTX 打包使用本站文件生成接口但不调用模型。表格工具可在本机导入 `.xlsx`，切换、编辑并导出最多 8 张可见工作表；公式只读取已有缓存值，不运行公式。导入文件和解压内容都有大小上限。总控明确收到“打开 JSON 工具”“打开 PowerPoint 工具”“打开 PDF 工具箱”等指令时使用本地路由，不额外付一次模型判断费用。对内容含义的讨论、跨项目自然语言指令、Agent 代做与新目标规划仍需要模型推理和/或工作台执行；JSON 工坊只做本地语法校验、美化和压缩，不会推断业务含义。

本轮新增用户可直接使用的联网搜索：通过本站服务器向 DuckDuckGo 查询并显示最多 5 条标题、摘要和原始来源链接；只查看搜索结果不调用 DeepSeek，搜索服务按账户和来源地址限流。结果是搜索引擎摘要，不等于已核实的全文；用户可自行打开来源，或明确点击“交给总控总结”，后者才会调用模型。全局总控也增加了 `search_web` 工具：用户要求联网查证、最新或外部事实时先检索，网页摘要作为不可信资料处理并返回来源链接；如果总控要调用工具后再继续答复，工具步骤上限为 2，后续步骤不再开放重复搜索，避免无界调用。总控聊天已修正同一条本轮消息同时进入历史和当前消息的问题，并按 AI SDK 实际模型步骤数记录请求数；这是去重输入和改准确账本，不保证供应商缓存命中或固定比例的费用下降。

用户在文档、代码、表格、JSON、演示稿或联网搜索页主动点击“把当前内容交给管理员”时，当前内容才随下一条管理员消息进入模型请求；管理员再交给工作区 Agent 时会转发同一附件。附件最多 100,000 个字符且 UTF-8 不超过 180 KB。附件会增加本轮模型输入量与费用，具体取决于内容长度及供应商计费；未点击发送时，工具的本地编辑、预览、格式化和导出不上传内容、不增加模型用量。权限校验仍按当前用户可编辑的工作区执行。

管理员有两条新增的无模型直达路径：用户询问 VHFXNEX 支持的工具或 Agent 时，从服务端能力目录生成答复；在实时工作区已选定路线后，用户明确说“开始/继续制作、按当前路线执行”等无歧义命令时，直接把原指令排入工作台，不再为意图分类多发一次对话请求。问句、路线讨论、未选择路线、附件正文需要理解的消息仍由模型判断；实时工作区仍要求已配置 API Key，且任务队列继续执行原有的工作台调用。快捷路径只省去这次对话 Agent 请求，不减少后续完成工作所需的工具/模型调用。管理员可调度规划 Agent、工作台 Agent 与适用的代码复核 Agent，以及搜索、文档/PDF/表格/演示稿生成和项目代码等执行工具；“最高层”只表示产品内的统一调度角色，服务端仍按当前账号权限验证项目访问。

总控首次读取用户分享的工具/文件附件后，会在当前对话暂存附件上下文。后续消息默认只把附件名称提供给总控模型；如果总控决定交接，完整附件会随交接任务传给工作台 Agent，但不会再次作为总控模型输入，从而避免重复 Token。用户可点“重新发送全文”让总控重新读取（这会增加用量），也可移除附件；成功交接、切换工作区或开始新对话会清除暂存上下文。首次发送全文仍会按内容长度产生相应用量。

工作台对可恢复的临时错误（网络/超时、HTTP 408/425/429 和可重试的 5xx）采用有上限的自动重试：最多 3 次总尝试，429 延迟 60 秒，其他临时错误延迟 15 秒。鉴权、无效请求、冲突等不可恢复错误和用户取消不会自动重试；达到上限后明确标记失败并保留已保存阶段成果。模型漏掉必需工具时，工作台只在上一次修复调用有新增任务、成果、事件或项目批次等实际进展时继续修复；没有进展就停止重复请求。代码生成在单轮修复没有进展时只额外尝试一次，并把具体工具校验反馈交给模型。代码、电子表格、演示稿、PDF、具体日程、联网搜索和可行性复核等在续作时仍会被明确检查的必需交付物最终缺失时，后台交接会基于已保存断点自动续跑一次（总尝试上限为 2）；行动方案等仅属于首次执行的要求不会误触发续作重试。鉴权、参数/权限错误和用户取消不进入该恢复路径。每次实际发给模型的请求仍可能计费，所以这些上限降低了无界重放风险，但不代表重试请求免费。
